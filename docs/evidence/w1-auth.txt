PAD-VETO REASON SPLIT (new, spec section 8.3)
---------------------------------------------
Mechanism: a trust-boundary helper `external_reason(&VerifyOutcome)` in
namtor-daemon/src/verify.rs maps the internal outcome to the reason
allowed in the socket AuthReply:
  - Verdict::NoMatch whose internal reason starts with "pad veto" -> None
    (generic; gate name + raw scalar stripped).
  - Other NoMatch reasons ("no face", "below threshold", ...) pass through.
  - Unavailable / Refused / RateLimited reasons pass through.
  - Match -> None.
The daemon dispatcher (dispatch.rs) calls `external_reason(&outcome)` when
building the AuthReply, so the PAM client and CLI never see "pad veto: ...".
The detailed reason is recorded INSIDE the daemon at debug level only, via
`tracing::debug!(target: "namtor::journal", ...)` in dispatch.rs
(verdict, score, internal_reason). No biometric data is logged — only the
gate name + scalar raw value, which is permitted.

Defense in depth: namtor-cli/src/verify.rs no longer prints reply.reason
on NoMatch (prints only "NO MATCH (score=...)"), so a daemon regression
cannot leak PAD-veto detail through the CLI debug tool.
